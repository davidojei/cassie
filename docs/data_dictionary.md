# Data Dictionary

Two layers: **source** (real, from Olist — never modified) and
**synthetic enterprise** (fictional, clearly labeled, built to support
business-analyst-style questions the public dataset can't answer alone).

---

## 1. Source layer — Olist Brazilian E-Commerce Dataset

| Table | Grain | Key columns | Notes |
|---|---|---|---|
| `olist_customers_dataset` | one row per order-customer | `customer_id` (PK, per-order), `customer_unique_id` (persistent identity), `customer_zip_code_prefix`, `customer_city`, `customer_state` | **See identity rule below — this is the most important modeling trap in the dataset.** |
| `olist_orders_dataset` | one row per order | `order_id` (PK), `customer_id` (FK), `order_status`, `order_purchase_timestamp`, `order_approved_at`, `order_delivered_carrier_date`, `order_delivered_customer_date`, `order_estimated_delivery_date` | Source of recency/frequency and delivery-delay features. |
| `olist_order_items_dataset` | one row per line item | `order_id` (FK), `order_item_id`, `product_id` (FK), `seller_id` (FK), `price`, `freight_value` | Sum by `order_id` for order value. |
| `olist_order_payments_dataset` | one row per payment installment | `order_id` (FK), `payment_sequential`, `payment_type`, `payment_installments`, `payment_value` | An order can have multiple payment rows (split/voucher payments). |
| `olist_order_reviews_dataset` | one row per review | `review_id`, `order_id` (FK), `review_score` (1–5), `review_comment_message`, `review_creation_date`, `review_answer_timestamp` | Source of CX features. |
| `olist_products_dataset` | one row per product | `product_id` (PK), `product_category_name`, dimensions/weight | Join `product_category_name_translation` for English names. |
| `olist_sellers_dataset` | one row per seller | `seller_id` (PK), `seller_zip_code_prefix`, `seller_city`, `seller_state` | |
| `olist_geolocation_dataset` | many rows per zip prefix | `geolocation_zip_code_prefix`, `lat`, `lng`, `city`, `state` | Not 1:1 — average/first-value per zip when joining. |
| `product_category_name_translation` | one row per category | `product_category_name`, `product_category_name_english` | Lookup only. |
| Olist Marketing Funnel *(optional)* | one row per lead | `mql_id`, `seller_id`, funnel stage/dates | Only if Phase 2 audit finds a usable join to customers/sellers. |

### ⚠️ Customer identity rule

`customer_id` is minted **per order** — the same real person gets a new
`customer_id` on every purchase. `customer_unique_id` is the persistent
identity. **All churn/retention/repeat-purchase analysis must group and
join on `customer_unique_id`.** Using `customer_id` for this will make
every customer look like a one-time buyer and silently break the entire
churn definition. This rule is enforced in `src/cassie/data/validation.py`
and re-checked in the data-quality pipeline (see
`docs/data_quality_plan.md`).

## 2. Synthetic enterprise layer

All tables below are **fabricated for this project** to simulate fields a
real Meridian Commerce Group system would have but the public dataset
doesn't. They are generated by `scripts/generate_synthetic_data.py`,
written to `data/synthetic/`, and loaded into the `raw` schema alongside
(never merged into) the real Olist tables. Every synthetic table is
prefixed and documented so it's unambiguous in any query or chart that
it isn't real transactional data.

| Table | Grain | Fields |
|---|---|---|
| `customer_support` | one row per ticket | `customer_unique_id`, `ticket_id`, `created_at`, `issue_type`, `priority`, `resolution_hours`, `resolved`, `customer_satisfaction`, `escalated` |
| `marketing_campaigns` | one row per customer-campaign touch | `campaign_id`, `customer_unique_id`, `campaign_date`, `channel`, `campaign_type`, `offer_percentage`, `opened`, `clicked`, `converted`, `campaign_cost` |
| `customer_costs` | one row per customer | `customer_unique_id`, `acquisition_cost`, `annual_service_cost`, `support_cost`, `discount_cost`, `estimated_processing_cost` |
| `customer_segments` | one row per customer | `customer_unique_id`, `segment`, `customer_tier`, `account_manager`, `strategic_account` |
| `retention_interventions` | one row per intervention | `intervention_id`, `customer_unique_id`, `intervention_type`, `cost`, `success_probability`, `created_at`, `outcome` |
| `business_policies` | narrative/config, not row-per-entity | retention discount eligibility, customer tier rules, refund rules, SLA rules, escalation rules, intervention approval limits — stored as markdown docs (`docs/*_policy.md`) for RAG, plus a config table for machine-readable thresholds |

Generation approach (to be finalized in Phase 2/6): sampled and
correlated against real order/review/delivery behavior so the synthetic
signal is plausible (e.g., customers with more late deliveries get a
higher chance of a support ticket) rather than pure random noise —
documented explicitly wherever an assumption is baked in.
